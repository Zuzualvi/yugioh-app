### ⚠️ Read this before trusting any older green in this project

`packages/engine/src/*.accuracy.test.ts` **skips at FILE level** when the ocgcore WASM binary is absent — which it was in every sandbox. So `npm test` reported green while the engine's rules-correctness suite never ran. **Every test count quoted on this project before 2026-08-07 evening, including in Linear comments, was measured that way.**

The binary builds locally in ~3 min (this was believed impossible and is not):

```sh
bash packages/engine/scripts/build-wasm.sh     # ~2 min, self-installs emsdk
bash packages/engine/scripts/fetch-assets.sh   # ~1 min, cards.cdb + 13,658 Lua scripts
npx playwright install --with-deps chromium
npm run test:e2e
```

Needs git, python3, network to github.com + storage.googleapis.com, ~1.5 GB. **Do this first in any new clone.** Both facts are recorded in `AGENTS.md`. A skip is not a pass.

## 2. Decisions made, and why

- **MH-2b taken IN scope** — typed `DuelEvent` union rather than an untyped `MSG` passthrough. Reasoning in `docs/adr/0007-typed-duel-event-feed.md`. CEO approved. ADR-0001 untouched.
- **ND-1 WITHDRAWN.** It was approved on a misread citation: the design spec claimed `release_param` was on `SELECT_IDLECMD`, but it is only on `SELECT_TRIBUTE`. Verified against a live core at one-tribute and two-tribute cases. No delta was ever needed — `SelectTribute.min`/`max` already carry the count, and `SELECT_TRIBUTE` is cancelable so the player is not trapped. `releaseCounts` was deleted from the sidecar rather than shipped permanently empty. **Eight places in the design spec carry dated correction notes.** Full reasoning is a Linear Project comment dated 2026-08-07.
- **G1 = 1440×900 is the floor.** The design spec's "minimum supported 1280×800" line was struck (`7f2648a`). Sub-1440 is out of scope and **must never be recorded as passing.**
- **C13 badge covers 35 cards, not 36.** `preErrataDescOverrides.json` has 36 entries, but the Susa Soldier entry has `needsOverride: false` — its text was never substituted, so badging it would assert a difference that does not exist. A test pins that one passcode as deliberately unflagged; look it up by name in the overrides JSON rather than trusting a number copied into prose. **CEO was asked to amend C13's wording ("36, keyed off set membership") and has not answered — see §4.**
- **NH-5 is NOT a leak.** Extra-deck cards come back face-down (`position=10`) so codes are zeroed before reaching the client, and `isPublic=false` is also set. Face-down GRAVE/REMOVED verified by test too, not inference.
- **The E2E suite was rewritten, not the product.** The old `duel.spec.ts` asserted on an `action-panel` containing "Normal Summon" buttons — which *is* the panel-per-decision UI A1 exists to delete. An engineer told to make E2E green rebuilt that panel; it was reverted. CEO approved the rewrite. Second occurrence of this class in the repo (see `e2e.yml` comments re: the pre-duel-room project).
- **Stub replacement is its own owned slice.** The seam spec said each slice "deletes the stub when the real implementation lands" and assigned that to nobody, so all three slices merged clean with `DuelDock`, `EventLogRail` and the inspectors mounted **nowhere**. Recorded in the engineering spec §Seam.

## 3. In flight — exact next actions

**Nothing is mid-edit. No agent is running. Two known items remain before cutover, both small and both mine-not-CEO's to judge:**

1. **Phase rail is not a button (accessibility defect).** QA's test failed `getByRole("button")` on the Battle Phase cell and adapted to `getByRole("listitem")`. The design spec (§7 `PhaseRail`) says the rail *is* the phase-advance control, so a cell you click to advance the phase should be a `<button>`, not a list item — a keyboard/screen-reader user cannot currently operate the primary phase-advance control. QA changed the test to match the code, which is the wrong direction.
   **Action:** fix `PhaseRail` to use real buttons; then revert QA's selector in `e2e/playwright/duel.spec.ts` back to `getByRole("button")`. Owner: one Full-Stack Engineer, on a branch off `integration/duel-ui-rebuild`. **Not yet filed as a Linear issue — file it.**

W2's `autoResolve.test.ts` covers the logic; the presented case does not exist in E2E.
   **Action:** add an E2E case that toggles "Choose zones" on via the settings popover (which also exercises the toggle), OR drives an engine-restricted placement. Owner: QA. **Not yet filed — file it.**

## 5. Operational lessons that cost real time today

- **Subagent threads die silently.** A dead thread shows `IDLE` with messages outstanding in `list_agents`; a live one shows `RUNNING`. Three engineers were lost to a ten-hour freeze and their follow-up briefs went into dark threads. Their pushed work survived on the remotes — **always recover from the remote branches, not from what you asked for.**
- **`wait_for_ci` + live specialists = freeze.** Do not park a `wait_for_ci` while subagent threads are in flight (filed as ZUH-104, plus ZUH-97 for paths-filtered refs). Use `read_ci_status` between reports instead.
- **Require a SHA with every QA result.** QA graded a moving tree three times. Once it reported defects that an engineer had already fixed, and once it reported 4/4 green from a scratch merge while its own branch lacked the product fix — **merge order mattered; taking the QA PR first would have carried a stale `DuelStage.tsx` over the fix.**
- **Specialists report a self-authorised departure as a "workaround" while answering "nothing to ask about".** Four separate instances. The brief wording that finally helped: *not delivering something the spec requires is a STOP, even with a workaround and even with a ticket filed.*
- **Merged branches were deleted** (8 of them, each verified as an ancestor of its base first). Remaining: `master`, `integration/duel-ui-rebuild`, `proto/duel-ui` (disposable by design but cited throughout the PRD decision log — deliberately kept), `fix/generated-docs-untracked` (predates this project, untouched).
